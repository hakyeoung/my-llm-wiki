# PlaNU Decisions

## 결정론적 규칙은 prompt가 아니라 코드 또는 데이터로 분리한다

PlaNU에서는 학과별 수강 가능 여부, 캠퍼스 이동 가능 여부 등의 규칙을 JSON으로 분리했다.

이 선택의 근거는 다음과 같았다.

- LLM prompt와 비즈니스 규칙을 분리할 수 있다.
- 규칙 변경이 쉬워진다.
- 테스트 가능성이 높아진다.
- 결과 재현 가능성이 높아진다.
- LLM 환각과 무관하게 동작한다.

현재 판단: 변경 가능하지만 결정론적인 비즈니스 규칙은 prompt보다 별도의 데이터나 코드로 관리하는 것이 적절하다.

일반화한 문서: [결정론적 규칙을 데이터로 분리하기](../../topics/backend/rules-as-data.md)

## 자연어 UI와 구조화 UI를 혼합한다

PlaNU에서는 처음에 사용자가 모든 조건을 prompt로 입력하는 형태를 고민했다. 하지만 프로젝트를 진행하면서 명확한 값은 일반 UI가 더 적절할 수 있다고 판단했다.

일반 UI가 더 적절한 입력:

- 학과 선택
- 교양 영역 선택
- 파일 업로드
- 전공 과목 선택

자연어가 유용한 입력:

- "아침 수업은 별로예요."
- "가능하면 수업을 몰아서 듣고 싶어요."

현재 판단: 자연어 UI와 구조화 UI를 목적에 따라 혼합하는 것이 좋다. 명확한 값은 form이나 선택 UI로 받고, 모호한 선호만 LLM에게 맡기는 편이 더 안정적이다.

관련 문서: [LLM과 결정론적 로직의 역할 분리](../../topics/llm/llm-vs-deterministic-logic.md)

## Hard constraint는 Agent가 임의로 변경하지 않는다

PlaNU를 더 Agent스럽게 만들기 위해 사용자의 조건을 Agent가 스스로 수정하고 더 좋은 시간표를 제안하는 구조를 고민했다. 하지만 Agent가 Hard 조건까지 임의로 변경하면 사용자 의도를 침해할 수 있다고 판단했다.

결정한 방향:

- Hard constraint는 Agent가 임의로 변경하지 않는다.
- Soft preference만 수정 후보로 제안한다.
- 실제 변경 여부는 사용자에게 확인한다.

현재 판단: Agent가 사용자의 목표를 대신 정의해서는 안 되고, 목표를 달성하기 위한 선택지를 제안하는 수준이 더 적절할 수 있다.

관련 문서: [Agent를 언제 사용할 것인가](../../topics/agent/when-to-use-agent.md)

## LLM 실패 가능성은 prompt 강화만으로 해결하지 않는다

PlaNU에서는 LLM이 전공 과목을 올바르게 추출하지 못하는 상황을 고민했다. LLM이 항상 성공하도록 prompt와 validator를 계속 강화하는 방법도 있었지만, 지나치게 엄격한 검증은 다른 문제를 만들 수 있었다.

결정한 fallback 방향:

- LLM 추출 성공: 바로 진행
- LLM 추출 실패: 파싱된 과목 목록을 사용자에게 보여주고 직접 선택하게 한다

현재 판단: LLM 시스템에서는 실패 가능성을 없애려 하기보다, 실패했을 때 결정론적인 fallback 경로를 마련하는 것이 더 현실적이다.
