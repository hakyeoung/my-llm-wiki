# PlaNU Lessons

## Agent는 LLM 사용 여부가 아니라 자율적 선택 필요성으로 판단한다

PlaNU에서는 처음에 LLM이 사용자의 조건을 해석하고 여러 단계를 수행하도록 만들면서 Agent 형태로 발전시키려 했다.

하지만 실제 문제를 분석해보니 많은 절차가 이미 정해져 있었다.

- 전공 과목 입력
- 교양 후보 필터링
- 시간 충돌 검사
- 학과별 수강 가능 여부 검사
- 캠퍼스 이동 가능 여부 검사
- 조건을 만족하는 시간표 탐색
- 후보 점수 계산

이런 로직은 대부분 함수나 규칙 기반 프로그램으로 명확하게 구현할 수 있었다.

현재 판단: Agent는 LLM이 존재하거나 Tool을 여러 개 호출한다는 이유만으로 필요한 것이 아니다. 실행 순서가 거의 고정되어 있고, 어떤 Tool을 언제 사용할지도 미리 결정되어 있다면 Agent보다 일반적인 workflow나 service orchestration이 더 적절할 수 있다.

일반화한 문서: [Agent를 언제 사용할 것인가](../../topics/agent/when-to-use-agent.md)

## LLM은 의미 해석에, 결정론적 코드는 규칙 적용에 적합했다

PlaNU 초반에는 LLM에게 더 많은 역할을 맡기려고 했다. 진행하면서 다음 작업은 LLM보다 결정론적 로직에 맡기는 것이 더 적절하다고 판단했다.

- 시간 충돌 검사
- 학점 범위 검사
- 학과별 수강 가능 여부
- 연속 수업 간 이동 가능 여부
- 후보 조합 생성
- 조건 만족 여부 검사
- 점수 계산

반면 LLM이 의미를 가지는 부분은 자연어 입력을 해석하거나 사용자의 모호한 선호를 구조화하는 부분이었다. 예를 들어 "아침 수업은 싫고 금요일은 쉬고 싶어요"를 `earliest_start_time`, `required_free_days` 같은 구조화된 조건으로 변환하는 작업은 LLM이 맡을 수 있다.

현재 판단: LLM은 의미 해석에 사용하고, 명확한 규칙 적용은 결정론적 코드에 맡기는 것이 안정적이다.

일반화한 문서: [LLM과 결정론적 로직의 역할 분리](../../topics/llm/llm-vs-deterministic-logic.md)

## Structured output 검증은 구조, 의미, 데이터 존재 여부를 분리해야 했다

PlaNU에서는 자연어 조건을 구조화하기 위해 Pydantic과 structured output을 사용했다. 이 접근은 LLM이 잘못된 형태의 데이터를 반환하는 문제를 줄이는 데 도움이 되었다.

하지만 과목명이나 조건 값을 너무 엄격하게 검증하면, LLM이 의미상 맞는 값을 추출했더라도 validator가 거부하는 일이 생겼다. 이 과정에서 다음 검증을 구분할 필요를 느꼈다.

- 구조 검증
- 의미 검증
- 실제 데이터 존재 여부 검증

현재 판단: Pydantic 같은 schema validator는 구조와 기본적인 타입 검증에 집중시키고, 의미적 유효성은 별도 로직에서 처리하는 편이 더 유연할 수 있다. 자연어를 정확한 DB 값에 바로 매핑하도록 강제하기보다, LLM의 추출 결과를 후보 데이터와 매칭하거나 보정하는 중간 단계가 필요할 수 있다.

일반화한 문서: [Structured output 검증과 schema 설계](../../topics/llm/structured-output-validation.md)

## LLM 검증 단계를 추가하면 품질 가능성과 latency 비용이 함께 늘어난다

PlaNU에서는 LLM이 추출한 결과를 다른 LLM이나 별도의 판단 단계가 검증하는 구조를 고민했다.

- LLM A가 사용자 조건을 구조화
- LLM B가 그 결과가 적절한지 평가

이 방식은 환각이나 잘못된 구조화를 줄이는 데 도움이 될 가능성이 있다. 다만 실제 Agent 흐름에서 LLM 판단 단계를 추가해보니 실행 시간이 매우 길어졌다.

현재 판단: Reflection이나 LLM-as-a-Judge를 모든 단계에 적용하는 것은 비용과 latency 측면에서 비효율적일 수 있다. 오류 비용이 높은 결정에만 선택적으로 적용하고, 단순한 규칙으로 검증 가능한 내용은 코드로 검증하는 편이 낫다.

관련 문서: [Agent를 언제 사용할 것인가](../../topics/agent/when-to-use-agent.md)

## Tool 수보다 Tool의 책임 경계가 더 중요했다

PlaNU를 Agent 형태로 바꾸는 과정에서 Tool이 계속 늘어났다.

- 사용자 조건 저장
- 사용자 조건 수정
- 시간표 생성
- 후보 점수화
- 후보 검증
- 최종 후보 선택

처음에는 Tool 수 자체가 문제처럼 보였지만, 실제 핵심 문제는 Tool 간 책임이 겹치고, 비슷한 검증 로직이 여러 Tool에 존재하며, Agent가 어떤 Tool을 사용해야 하는지 애매해지는 것이었다.

현재 판단: Tool의 개수보다 Tool의 경계와 책임이 명확한지가 더 중요하다. Tool 설계에서는 "이 Tool은 어떤 질문에 답하는가?"가 명확해야 한다.

관련 문서: [Agent를 언제 사용할 것인가](../../topics/agent/when-to-use-agent.md)

## 사용자 선호 schema는 단순하고 겹치지 않아야 했다

PlaNU에서는 사용자의 시간표 조건을 구조화하면서 Hard 조건과 Soft 조건을 나누었다. 프로젝트 중간에는 조건을 더 세분화하는 방안도 고민했지만, 조건 종류가 많아질수록 LLM이 올바르게 분류해야 할 부담이 커졌다.

예를 들어 다음 필드는 의미가 겹치고, LLM이 어느 필드에 값을 넣어야 하는지 혼란을 줄 수 있었다.

- `earliest_start_time`
- `no_morning_classes`
- `morning_end_time`

현재 판단: LLM이 변환해야 하는 schema는 가능한 한 의미가 겹치지 않고 단순해야 한다. 가능하면 하나의 개념은 하나의 필드로 표현한다.

일반화한 문서: [Structured output 검증과 schema 설계](../../topics/llm/structured-output-validation.md)

## 점수화 결과는 객관적 정답이 아니었다

PlaNU에서는 여러 시간표 후보를 비교하기 위해 점수화를 사용했다. 하지만 사용자마다 중요하게 생각하는 기준이 다르기 때문에, 고정된 가중치가 객관적인 "좋은 시간표"를 의미하지 않는다는 문제가 있었다.

- 어떤 사람은 아침 수업이 가장 싫을 수 있다.
- 어떤 사람은 공강 시간이 긴 것이 가장 싫을 수 있다.
- 어떤 사람은 금요일 공강을 가장 중요하게 생각할 수 있다.

현재 판단: 점수는 절대적인 품질이 아니라 특정 기준에 따른 비교값으로 해석해야 한다. 가능하다면 점수의 구성 요소나 이유를 사용자에게 보여주는 것이 신뢰성 측면에서 더 낫다.

이 내용은 아직 PlaNU 한 프로젝트에서 관찰한 판단으로 남겨둔다.

## 후보가 모두 나쁘다면 탐색보다 조건 재검토가 필요할 수 있다

PlaNU에서는 생성된 시간표 후보가 모두 사용자의 기대에 맞지 않는 경우를 고민했다. 처음에는 후보 점수를 더 조정하거나 다시 탐색하는 방향을 생각했지만, 후보가 전부 마음에 들지 않는다면 탐색 알고리즘보다 입력 조건 자체를 재검토해야 할 가능성이 높다고 판단했다.

현재 판단: 시스템은 무한히 후보를 재생성하기보다 사용자에게 "약간 수정하고 싶다", "조건을 많이 바꾸고 싶다" 같은 선택지를 제공하고, Soft 조건을 중심으로 조정할 수 있어야 한다.

이 내용은 추천 시스템이나 Agent UX 전반에도 적용 가능성이 있지만, 아직은 PlaNU에서 관찰한 패턴으로 기록한다.

## 시스템의 상태와 제약을 사용자에게 숨기지 않아야 했다

PlaNU에서는 DB를 사용하지 않고 in-memory session을 사용했기 때문에 세션이 만료될 가능성이 있었다.

이 문제를 완전히 숨기기보다 다음과 같이 UX에 반영하는 것이 낫다고 판단했다.

- 세션 만료 가능성 안내
- 만료 시 명확한 오류 메시지
- 파일 재업로드 안내
- 초기 화면으로 돌아가는 버튼

현재 판단: 기술적 제약이 사용자 경험에 영향을 준다면, 시스템이 이를 숨기기보다 명확하게 설명하고 복구 경로를 제공해야 한다.

이 내용은 아직 PlaNU 한 프로젝트의 UX 판단으로 남겨둔다.
