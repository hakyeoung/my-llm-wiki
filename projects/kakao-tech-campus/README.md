# 주린이

초보 투자자에게 "내 종목이 왜 이렇게 움직였는지"를 설명하는 보고서를 자동 생성하는
프로젝트. 1차 실험(2026-09)에서 얻은 판단을 정리한다.

---

## 무엇을 검증했나

보고서가 서비스의 핵심이라, 만들기 전에 **LLM이 쓸 만한 보고서를 내놓는지**부터
확인했다. 두 단계로 진행했다.

| | v1 | v2 |
|---|---|---|
| 자료 출처 | 뉴스 검색 API | 텔레그램 공개 채널 |
| 대상 시점 | 과거 사건 재현 | 당일 생성 |
| 채점 | 사전 작성한 정답 | 도메인 지식 있는 PM |
| 유효 실행 | 22런 | 18런 |

---

## 하네스가 실제로 산 것

시스템 프롬프트 적용군(B)과 미적용군(A)을 나눠 측정했다.

| 항목 | A (프롬프트 없음) | B (적용) |
|---|---|---|
| 구조화된 판정 출력 | 0/10 | 12/12 |
| 되묻고 종료 | 3/10 | 0/12 |
| 근거 원문 확인 | 0/10 | 4/12 |
| 사실 조작 | 0 | 0 |

**되묻기 차단이 가장 컸다.** 자동 실행 환경에는 대답할 사람이 없다.
A군은 정보가 부족하면 "어느 쪽을 말씀하시는 건가요"로 끝냈고, 그대로 실패했다.
이 규칙 없이는 배치 파이프라인이 성립하지 않는다.

**판정 구조화**도 컸다. A군도 "확인되지 않았다"고는 썼지만 산문이라 기계가 못
읽는다. `verdict: no_clear_cause` + 빈 근거 배열이 있어야 "원인 없음" 화면을
분기할 수 있다.

**증명하지 못한 것**도 있다. "보합일에 억지로 원인을 만들지 말라"는 조항을
넣었는데, A군도 만들지 않았다. 이 조항은 값을 증명하지 못한 채 남았다.
→ [프롬프트를 언제 고칠 것인가](../../topics/llm/evaluating-prompt-changes.md)

## 가장 중요했던 테스트: 설명할 수 없는 날

등락률이 거의 없는 날, 또는 급락했는데 자료에 원인이 없는 날.

초보 투자자에게 **없는 원인을 만들어 주는 것**이 이 서비스의 최악의 실패다.
그걸 믿고 매매하니까.

실측에서 두 유형이 다르게 나왔다.

**보합일** — 관련 자료를 찾긴 찾았는데 전부 배경으로 내리고 근거 배열을 비웠다.
한 실행은 날짜 규칙을 명시적으로 인용하며 "5일 앞선 시점이라 참고용 배경으로만"
이라고 스스로 판단했다.

**급락인데 자료가 호재뿐인 날** — 더 인상적이었다. 입력에 목표주가 상향,
해외 예탁증서 +7%, 가격 전망 상향이 있었는데 주가는 -5.12%였다.

> 메시지들은 오히려 상승 요인 위주였고, 이것이 실제 하락과 방향이 맞지 않아
> 원인으로 채택하지 않았습니다

수급 이벤트를 검토하고 기각한 논리도 타당했다.

> 1.2조원 수준의 매도 물량이나 소폭 순매도로는 5%대 급락 폭을 설명하기 어려우며

**등락 폭과 근거 크기를 비교하는 절차**가 작동한 것이다.

## 자동 검증으로 잡히는 것과 안 잡히는 것

보고서를 JSON으로 받고, 입력 자료와 대조하는 검증을 붙였다.

| 검사 | 잡는 것 |
|---|---|
| 입력에 없는 URL | 출처 조작 |
| 인용문이 원문에 없음 | 환각 |
| 근거 없는 주장 | 스키마 위반 |

**이것만으로는 부족하다.** 실측 사례 하나.

자동 검증을 통과한 보고서가 "전날(9/13) 미국 증시에서 하락"이라고 썼다.
9월 13일은 일요일이었고, 원문은 다른 시장의 등락이었으며, 입력 메시지에는
오히려 "미국 증시는 강세 마감"이라고 적혀 있었다. 입력에 있던 중요 재료 3건도
빠졌다.

**URL도 인용문도 진짜였다. 해석이 틀렸다.**

그래서 검수를 2단으로 나눴다.

- **1차(실험자)** — 자동 검증 + "입력과 보고서를 나란히 놓고 대조".
  종목 지식이 없어도 된다. 위 오류 셋 중 둘은 달력과 원문 대조만으로 나왔다.
- **2차(PM)** — 도메인 지식이 필요한 판단. 3단(통과/아쉬움/반려)으로 단순화하고
  반려에만 사유를 적게 했다. 점수보다 반려 사유가 개정 재료로 값지다.

## 소스를 늘리면 좋아지는가

"자료가 많으면 핵심을 못 찾을 것"이라는 우려가 있었다. 조건을 나눠 측정했다.

| 조건 | 평균 비용 | 평균 소요 | 판정 변화 |
|---|---|---|---|
| A: 5채널, 메시지 단위 | $0.087 | 33초 | 기준 |
| B: 16채널, 메시지 단위 | $0.144 | 40초 | 없음 |
| C: 16채널, 항목 단위 | $0.126 | 23초 | 3건 |

**B에서 판정이 하나도 안 바뀌었다.** 근거 개수는 늘었지만 결론은 같았고
비용만 1.7배가 됐다.

**C가 가장 나았다.** B보다 싸고 빠르면서 판단이 더 정확해졌다.
한 건은 근거 4개로 확신이 세졌고, 다른 건은 무리한 귀인을 거두고
"원인 없음"으로 내려갔다.

그리고 **헤매지 않았다.** 한 보고서의 근거 4개가 각각 다른 채널에서 나왔고
겹치는 내용이 없었다. 유가·AI 투자 전망·수급·개별 계약 지연이 한 번에 모였다.

다만 **추가한 11개 채널 중 4개만 실제로 인용됐다.** 소스를 늘리는 것보다
어떤 소스가 값을 하는지 재는 것이 먼저다.
→ [컨텍스트에 무엇을 넣을 것인가](../../topics/llm/context-scoping.md)

## 서비스 설계에 반영할 것

**배치 생성이 맞다.** 보고서 하나에 23~40초다. 실시간 응답으로는 무리다.
장 마감 후 미리 만들어두는 구조로 간다.

**비용은 보고서당 $0.13 수준.** 종목 수 × 영업일로 곱하면 규모가 나온다.

**출력 스키마를 서비스용과 검증용으로 나눈다.** 인용문·출처 성격 같은 필드는
환각 탐지에 쓰지만 화면에는 안 나간다. LLM은 전부 만들고 API 응답에서 거른다.

**"원인 없음"을 어떻게 보여줄지 정해야 한다.** 실측에서 6건 중 2건이었다.
정직하지만 유저가 쓸모없다고 느낄 수 있다. 미해결 과제.

## 실험 설계에서 배운 것

**케이스의 정답을 기억으로 채우지 않는다.** 한 케이스에서 사건 발생일과 함정
전제를 모두 추론으로 적었다가 두 번 틀렸다. 실적 발표일이 하루 달랐고,
"실적 부진이라고 답하면 오답"이라고 설계한 함정이 실제로는 정답이었다.
정답은 검색으로 확정하고 출처를 붙인다.

**정답 라벨이 틀릴 수 있다.** 분류 실험에서 채널별로 섹터를 미리 라벨링했는데,
특정 채널의 정확도가 40%로 낮게 나왔다. 확인해보니 분류기가 아니라 라벨이
틀렸다. 그 채널은 반도체가 아닌 품목을 다수 다루고 있었다.

**실패를 0으로 감추지 않는다.** 집계 스크립트가 오류 시 0을 반환하도록 짜서
"도구 호출 0회"로 오진한 적이 있다. 실패는 별도 값으로 구분한다.

**입력 길이 한계를 미리 확인한다.** 자료를 늘리자 명령행 길이 제한에 걸려
전량 실패했다. 표준입력으로 넘기면 해결된다. 그리고 실패했는데 **비용이 오히려
줄어서** 효율이 좋아진 것처럼 보였다. 지표만 보면 놓친다.
