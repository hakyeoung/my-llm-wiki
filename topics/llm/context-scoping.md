# 컨텍스트에 무엇을 넣을 것인가

LLM에게 자료를 주는 방법은 둘이다. 도구를 주고 스스로 찾게 하거나,
밖에서 골라 프롬프트에 실어주거나. 이 선택이 품질·비용·통제 가능성을 모두 바꾼다.

## 검색을 위임하면 통제를 잃는다

과거 시점을 재현하는 작업에서, 검색 API를 도구로 주고 "대상일 이후 기사는 쓰지
말라"고 프롬프트에 적었다. 그 검색 API는 기간 필터를 제공하지 않아 미래 기사가
결과에 섞여 들어왔다.

결과: **12번 실행 중 10건이 대상일 이후 기사를 근거로 인용했다.**

프롬프트로 "안 본 척하라"고 요구하는 건 무리한 주문이다. 이미 컨텍스트에 들어온
정보는 결론에 영향을 준다. 인용하지 않아도 마찬가지다. 제목만 읽어도 결론이
거기 적혀 있으면 그걸 재구성하게 된다.

같은 작업을 **밖에서 잘라** 넣는 방식으로 바꿨더니 위반이 0이 됐다.
컷오프 이후 데이터가 애초에 프롬프트에 없으니 볼 방법이 없다.

**규칙으로 보장할 수 있는 것을 프롬프트로 부탁하지 않는다.**

다만 밖에서 거르는 방식은 에이전트가 조회 범위를 조정할 수 없다는 한계가 있다.
"직접 재료로는 설명이 안 되니 섹터를 더 보자" 같은 판단을 못 한다.
도구로 만들되 **컷오프를 도구 안에 박으면** 둘 다 얻을 수 있다.
→ [Agent를 언제 사용할 것인가](../agent/when-to-use-agent.md)

## 자료를 덩어리째 넣지 않는다

수집한 메시지 하나에 여러 개의 독립된 항목이 들어 있는 경우가 많았다.
뉴스 모음 한 건에 기사 11개, 시황 브리핑 한 건에 항목 32개.

이걸 통째로 넣으면 관련 있는 항목 2개 때문에 나머지 9개가 딸려 들어간다.

**항목 단위로 쪼개서** 관련된 것만 넣도록 바꿨다.

| | 쪼개기 전 | 쪼갠 후 |
|---|---|---|
| 입력 분량 | 23,111자 | 7,055자 |
| 비용 | $0.144 | $0.126 |
| 소요 | 40초 | 23초 |

쪼개는 건 **규칙으로 한다.** 자료의 형식이 규칙적이면(항목마다 링크로 끝남,
불릿으로 시작함) LLM을 부를 필요가 없다. 비용이 0이고 결과가 항상 같다.
→ [LLM과 결정론적 로직의 역할 분리](./llm-vs-deterministic-logic.md)

경계 기준은 두 번 조정했다. 처음엔 하이픈까지 경계로 써서 한 항목이 14조각으로
흩어졌고, 반대로 빼니 특정 채널이 거의 안 쪼개졌다. **확실한 경계를 먼저 쓰고,
애매한 경계는 확실한 것이 없을 때만 보조로** 쓰는 방식으로 정착했다.

### 쪼개면 잃는 것

메타데이터가 항목마다 있지 않다. 출처 표기가 원문 끝에 한 번만 붙는 형식이라,
쪼개니 그 정보가 한 조각에만 남고 나머지는 단서를 잃었다.
분류 정확도가 83%에서 29%로 떨어졌다.

**부모 단위에서 판별해 조각에 물려주는** 방식으로 해결했다(상속 후 93%).
쪼갤 때는 무엇이 부모 단위에서만 알 수 있는 정보인지 따져야 한다.

## 전처리로 좁히기 전에, 좁힐 필요가 있는지 확인한다

"자료가 많으면 핵심을 못 찾을 테니 미리 분류해서 좁혀주자"는 가설을 검증했다.

먼저 분류 체계를 데이터에서 뽑으려 했다. 배치를 나눠 같은 질문을 던지고
반복해서 나오는 축만 채택하는 방식이다. **28개 이름이 나왔고 여러 배치에서
반복된 축은 1개뿐이었다.** 의미로는 6개로 수렴했지만 이름이 매번 달라
자동 도출이 안 됐다.

목록을 고정해서 주니 일관성은 올랐다(77%). 하지만 경계에 걸친 항목에서는
여전히 갈렸다. 한 부품이 반도체인지 부품인지는 **분류기 문제가 아니라 실제로
애매한 것**이다. 카테고리를 늘리면 새 경계가 생긴다. 끝이 없다.

더 중요한 발견이 있었다. 도출된 카테고리가 **자료 출처 구분과 거의 일치했다.**
출처별로 다루는 주제가 정해져 있으니 당연했다. 그러면 분류할 이유가 없다.
출처 이름만 보면 된다.

그리고 **분류 없이도 잘 돌아갔다.** 키워드 매칭만으로 자료를 걸러 만든 결과가
형식 검증 6/6 통과, 사실 조작 0건이었다. 분류가 개입할 자리가 없었다.

**전처리 트랙을 접었다.** 대신 소스를 3배로 늘려서 정말 헤매는지 확인했더니,
헤매지 않았고 오히려 근거가 다양해졌다. 한 보고서의 근거 4개가 각각 다른
출처에서 나왔고 겹치는 내용이 없었다.

가설의 전제("많으면 못 찾는다")가 틀렸던 것이다.

## 정리

| 상황 | 방법 |
|---|---|
| 시점·범위를 보장해야 함 | 밖에서 자른다. 프롬프트로 부탁하지 않는다 |
| 자료에 여러 항목이 섞임 | 규칙으로 쪼갠다 |
| 쪼개면 사라지는 메타데이터 | 부모 단위에서 판별해 물려준다 |
| 자료가 많아 보임 | 좁히기 전에 그대로 넣어보고 실제로 헤매는지 본다 |
| 분류가 필요해 보임 | 분류 없이 되는지 먼저 확인한다 |
